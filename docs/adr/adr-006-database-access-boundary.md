# ADR 006 利用者権限とRLSおよび専用RPCでDBアクセスを制御する

## ステータス

採用

## 決定日

2026-10-16

## コンテキスト

画面やAPIの検査だけに依存せず、DBへのアクセスでも利用登録と設定権限を守る必要がある。

## 検討した選択肢

元資料に比較の履歴はない。以下は採用済みのアクセス境界と、その境界で許可しない方式の整理である。

採用：利用者権限でのアクセス、RLSによる読み取り制限、専用RPCへの書き込み集約。

不採用：通常利用者によるテーブルの直接変更。

不採用：通常の業務操作をサービスロールで実行し、APIだけで権限を検査する。

## 決定事項

Next.js APIは認証を検証し、利用者の権限でDBへアクセスする。全テーブルにRLSを有効にし、有効な登録利用者の読み取りだけを許可する。通常利用者の書き込みは権限検証を伴う専用RPCへ集約し、テーブルの直接変更を許可しない。RPCでも利用登録と設定操作の権限を検証する。サービスロールはサーバー内の通知定期処理に限定し、通知専用関数を通常利用者には実行させない。

## 決定理由

利用者の権限をDBまで伝え、書き込み経路を集約することで、API外のアクセスでも認可と業務制約を適用できるため。

## 結果

権限検査を複数の境界で維持できる。RLSとRPCの双方で権限設定を管理する必要がある。特権を持つ通知処理は通常の業務操作から分離される。
